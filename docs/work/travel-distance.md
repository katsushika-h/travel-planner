# Travel distance between stops

Status: Phases 1–2 done (TD1–TD4) — phase 1 merged (PR #26), phase 2 PR open to `main`; phase 3 next

Goal: Show travel distance and time between consecutive stops in a day, choose between walking and driving sensibly, and suggest the closest parking for driving legs.

Scope: Plan view (`components/views/TripDaysView.tsx`, `components/views/plan/`), pure leg and cluster logic with Node tests, an OpenRouteService (ORS) server route with a database cache, and a parking lookup. Legs are derived from stops, never stored as `TravelObject` items. No Google API billing.

## Findings

- Stops carry `location.lat`/`location.lng` (extracted from Google Maps URLs). Stops without coordinates break the chain; show the gap instead of guessing.
- A leg is two adjacent stops on the same `date` in `dayOrder` sequence. Undated Ideas and `kind: "note"` items are excluded.
- A `commute` or `flight` item between two stops is a user-planned transfer; do not compute a leg across it.
- The map is Leaflet + OpenStreetMap (`components/views/LeafletMap.tsx`, shared by Plan, Map and `DayJourneyView`). External lookups go through a server route, like `app/api/maps/resolve`.
- `StopRow.tsx` already reserves a slot for the travel-time line (comment near the end of the component).
- Per-trip UI preferences already live in `store/use-travel-store.ts` (keyed by `tripId`, persisted). Travel mode and leg overrides go there, so phases 1–2 need no `Trip` schema change. Limitation: they are per device.
- Tests are `tests/*.test.mjs` importing `.ts` directly; route handlers are tested by transpiling them and mocking `fetch` (see `tests/maps-resolve.test.mjs`).
- The `docs/FEATURES.md` suggested-time auto-planning item depends on leg durations; it is out of scope here.

## Provider: OpenRouteService

- Hosted ORS is the provider. Fallbacks: self-host ORS (same API, change the base URL) or Valhalla on the NAS; Overpass for parking. The public OSRM demo server is not permitted for app use.
- Free Standard plan (checked 2026-10-15, re-check before phase 2): Directions 2,000/day and 40/min; Matrix 500/day; POIs 500/day with a 2 km search radius. The cache keeps a single-user app far below this.
- Profiles: `foot-walking` and `driving-car`. No public transit in the hosted API.
- The key needs a free ORS account. Store it as the server-only env var `ORS_API_KEY` (local `.env`, NAS compose environment); never send it to the browser or log it.
- Stop coordinates are sent to HeiGIT; show ORS attribution next to the OSM attribution; the free plan is non-commercial.
- Sources: <https://openrouteservice.org/plans/>, <https://openrouteservice.org/restrictions/>, API docs <https://openrouteservice.org/dev/#/api-docs>.

## Default decisions

The user has not answered these yet; agents use the defaults until the coordinator says otherwise.

- Car: travel mode is per trip, default `walk`. `drive` is opt-in from the Plan view.
- Hotel: legs do not start or end at the hotel; only adjacent stops on the day are linked.
- Walking range for clustering: ≤ 1.5 km straight-line between consecutive stops.
- Walking cap (user decision, 2026-10-16): legs whose walking distance (detour-adjusted) exceeds 3 km (`MAX_WALK_METERS`) show distance only, with no walk time, and are left out of the walking total. Phase 1 has no drive mode, so long legs are not given a time at all.
- Hosting: hosted ORS; no NAS routing container.

## Phase 1 — straight-line legs (client only)

### TD1 Leg domain

Owns: `lib/travel-legs.ts`, `tests/travel-legs.test.mjs`.

Build pure functions with no React, fetch or Prisma imports:

- `haversineMeters(a, b)` for `{ lat, lng }` points.
- `estimateWalk(meters)` → `{ meters, seconds }` using a 1.3 detour factor and 4.8 km/h. Export both constants.
- `dayLegs(items)` taking one day's items already sorted by display order, returning one entry per adjacent pair of non-note items: `{ fromId, toId, status }` where `status` is `"ok"` (with `meters` and `seconds`), `"unmapped"` (either end lacks finite coordinates), or `"transfer"` (either end is type `commute` or `flight`; the transfer item itself has no computed leg on either side).
- `formatDistance(meters)` ("850 m", "1.2 km") and `formatDuration(seconds)` ("4 min", "1 h 05 min"), rounding walking time up to whole minutes.
- `dayTotals(legs)` → summed meters and seconds of `"ok"` legs plus the count of skipped legs.

Tests cover a known distance (for example two Tokyo stations within 1%), zero distance, notes skipped, unmapped and transfer gaps, invalid coordinates (`NaN`, out of range), formatting boundaries, and totals.

### TD2 Plan leg line

Owns: `components/views/TripDaysView.tsx`, `components/views/plan/StopRow.tsx`, `components/views/plan/DayStrip.tsx`, new `components/views/plan/LegLine.tsx`.

- Compute `dayLegs` for the active day in `TripDaysView` from the same ordered list the rows use, and pass each row its outgoing leg.
- `LegLine` renders in the reserved `StopRow` slot: walking icon (existing icon library), `~12 min · 900 m`, muted text, with the `~` marking an estimate. `"unmapped"` shows "No location — distance unknown"; `"transfer"` renders nothing. The last stop has no line.
- Add the day's walking total to the `DayStrip` day summary ("~1 h 10 min walking").
- Accessible text: the line reads as "About 12 minutes walking, 900 metres to <next stop title>".
- Mobile (below 768px) keeps the same line; it must not widen rows.

## Phase 2 — routed legs via ORS

### TD3 ADR, ORS route and cache

Owns: `docs/decisions/0008-travel-routing-provider.md`, `prisma/schema.prisma` (new model only), new migration, `lib/ors-client.ts`, `lib/route-leg-validation.ts`, `app/api/route-legs/route.ts`, `tests/route-legs.test.mjs`, `.env.example`, `docker-compose.nas.yml` (env var only).

1. Write ADR 0008 (provider, cache, fallbacks, attribution, key handling) and stop for coordinator approval.
2. `RouteLeg` model: `id`, `profile` (`foot-walking` | `driving-car`), `fromLat`, `fromLng`, `toLat`, `toLng` (rounded to 5 decimals), `meters`, `seconds`, `geometry` (encoded polyline string), `createdAt`; unique on `(profile, fromLat, fromLng, toLat, toLng)`. Treat rows older than 90 days as stale.
3. `lib/ors-client.ts` (server-only): directions call with `Authorization` from `ORS_API_KEY`, 10 s timeout, and typed errors for missing key, quota (429), and upstream failure. Confirm endpoint paths and response fields against the ORS API docs; do not guess.
4. `POST /api/route-legs` with `{ legs: [{ from: {lat,lng}, to: {lat,lng}, mode: "walk" | "drive" }] }` (max 25 legs): validate, serve cached rows, fetch misses sequentially, store them, and return `{ legs: [{ meters, seconds, geometry, cached }] }` in request order. A failed leg returns `{ error }` in its slot; missing key returns 503 with a clear message.
5. Add `ORS_API_KEY=` to `.env.example` and the app service environment in `docker-compose.nas.yml`. The migrator image must be rebuilt at deployment (note it in the report; do not build).
6. Tests with mocked `fetch` and a stubbed Prisma client: validation errors, cache hit skips fetch, cache miss stores, 429 and missing-key handling, order preserved.

## Phase 3 — walk/drive clusters and parking

### TD5 Walk/drive clusters (parallel with TD6)

Owns: `lib/travel-clusters.ts`, `tests/travel-clusters.test.mjs`.

- `clusterDay(items, { walkRangeMeters })`: group consecutive mapped stops while each straight-line hop is within range; `"unmapped"` and `"transfer"` gaps end a cluster.
- `planDayLegs(clusters, mode, overrides)`: in `walk` mode every leg walks. In `drive` mode, legs inside a cluster walk, legs between clusters drive from the previous cluster's parking anchor, and each multi-stop cluster ends with a walk back to its anchor. The anchor is the cluster's first stop until parking is chosen. `overrides` (`Record<"fromId>toId", "walk" | "drive">`) wins, but a `drive` override is refused (reported as a warning) when the car is not at the leg's start.
- Tests: all walkable, all far apart, mixed, gaps, overrides, and the car-left-behind warning.

### TD6 Parking route and validation (parallel with TD5)

Owns: `app/api/parking/route.ts`, `lib/parking-client.ts`, `tests/parking.test.mjs`, `lib/api-validation.ts` (parking field only), `types/travel.ts` (`LocationData.parking` only), `tests/api-validation.test.mjs` (parking cases only).

- `GET /api/parking?lat=&lng=` returns up to 5 car parks within 1 km, nearest first: `{ name, lat, lng, meters, fee, access }`. Use the ORS POIs endpoint with its parking category (find the ID from the ORS POI category list; do not hard-code a guess). Fall back to Overpass (`amenity=parking`, exclude `access=private`) when ORS fails. Cache results in memory for 24 hours keyed by coordinates rounded to 3 decimals.
- `LocationData.parking?: { name?: string; lat: number; lng: number }` with validation (finite, in range, name ≤ 300 chars). Existing locations without `parking` stay valid.
- Tests with mocked `fetch`: ORS success, ORS failure falls back, private parking excluded, validation accepts and rejects.

### TD7 Clusters and parking in the UI

Owns: `components/views/plan/*`, `components/views/TripDaysView.tsx`, `components/views/LeafletMap.tsx` (optional props only), `store/use-travel-store.ts` (leg overrides), `lib/api-client.ts` (parking function).

- Use `planDayLegs` in Drive mode; leg lines show walking or driving icons, the walk back to the car, and override controls (walk/drive) per leg. Store overrides per trip.
- For each driving cluster, show "Park at <name> · 350 m walk" with a picker from `/api/parking`; saving updates the cluster's first stop `location.parking` through the existing item update action. A saved parking spot becomes the cluster anchor.
- `LeafletMap` gains optional parking markers ("P", token colours).
