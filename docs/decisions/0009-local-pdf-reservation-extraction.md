# ADR 0009: Local, rule-based PDF reservation extraction

**Status:** Accepted (2026-10-20).

**Context:** Reservation import read `.ics` files and schema.org markup, but most confirmations arrive as PDFs. Evaluating extraction on twelve real booking PDFs showed that generic text rules produce plausible wrong values (decoy dates, pre-discount totals, booker addresses), while LLM extraction would read new layouts better but send personal booking data to an external API, and the app has no authentication to protect an API key.

**Decision:** Read PDFs in the browser with pdf.js (`pdfjs-dist`, loaded on demand, character maps served from `public/pdfjs/cmaps/`, generated by `scripts/copy-pdfjs-cmaps.mjs`). Extract one draft with `lib/pdf-reservation.ts`, which takes values only from labels or recognised layouts, keeps conflicting or ambiguous fields blank, and records per-field confidence and evidence. The review dialog shows that evidence and lets every field be edited before the item is created through the normal API. The rules and their evaluation protocol live in `docs/work/reservation-pdf-extraction-recipe.md`.

**Consequences:** No booking data leaves the device and no API key or running cost is added. Coverage is limited to wording and layouts the rules know: in blind tests the rules left most fields of new layouts blank, so new booking sites need rule updates, evaluated with the frozen-rules protocol before relying on them. Image-only scans are refused because there is no OCR. Flight-time conversion uses a small built-in airport-to-timezone table. The pdf.js worker and character maps add about 3 MB of static assets, loaded only when a PDF is imported. `npm run dev`, `npm run build`, and the Dockerfile copy the character maps before building.
